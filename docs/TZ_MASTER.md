## Зачем этот документ

Исходный запрос владельца — сделать премиальный интернет-магазин с каталогом из 1С, возможностью проката инструмента, автоматическим подбором описаний и фото товаров «из интернета» и дальнейшим приёмом оплаты. Часть этого запроса реализуема сразу, часть — технически нереализуема в буквальном виде, а часть зависит от решений, которые может принять только владелец (не инженер). Ниже — разбор по каждому пункту и реалистичный план вместо него.

### Где исходный запрос пришлось скорректировать

1. **«Полностью автоматический подбор фото/описаний товаров из интернета»** — в буквальном виде это неконтролируемый скрапинг чужих сайтов. Риски: нарушение авторских прав на чужие фото и тексты описаний (можно отвечать на претензию правообладателя), а также то, что скрапинг без проверки человеком тащит в карточку товара чужую ошибку или чужую цену. Решение: Фаза 3 делает это полуавтоматическим инструментом с подтверждением администратора перед публикацией, не автономным сборщиком.
2. **vseinstrumenti.ru как источник** — у этого сайта есть защита от автоматических запросов (капча при подозрении на бота). Обходить капчу — нарушение условий использования сайта и прямо запрещено нашими же правилами безопасности. Решение: vseinstrumenti.ru не используется как источник автосбора вообще; разрешённые источники — сайты производителей и официальных дистрибьюторов, которые не блокируют обращение, либо вставка текста/фото вручную администратором.
3. **«Мгновенная синхронизация с 1С»** — касса работает на локальной «1С:Управление нашей фирмой» без интернета (подтверждено владельцем). Прямой автоматической синхронизации не будет до тех пор, пока на кассовый компьютер не поставят отдельную программу-синхронизатор (это отдельная работа, требующая физического доступа к компьютеру в магазине, не входит в эту фазу). Решение: Фаза 2 — ручной экспорт файла из 1С и загрузка его в админку сайта, с защитой от потери данных при сбое.
4. **«Приём оплаты на сайте»** — провайдер эквайринга пока не выбран (владелец сказал «решим позже»). Решение: сайт запускается в демо-режиме оформления заказа (заказ фиксируется, оплата согласовывается по звонку), Фаза 4 резервирует место для реального подключения, когда провайдер появится.
5. **«Боты в VK/Telegram/MAX»** — пока не заведены ни токены ботов, ни права администратора в группах. Решение: Фаза 5 — конкретный список того, что должен подготовить владелец, и что построит инженер, без утверждений, что это уже работает.

## Фаза 2 — Канал данных из 1С

**Текущий статус:** не начато.

### Принципы (обязательны для реализации)
- **`onec_id` — неизменяемый первичный ключ товара.** Это артикул/код из 1С, который никогда не меняется и не генерируется сайтом. Все обновления цены/остатка матчатся по нему.
- **Ручной импорт, не автосинхронизация.** Касса на локальной 1С без интернета физически не может сама отправлять данные на сайт. Единственный путь сегодня — владелец вручную выгружает файл из 1С (см. `docs/INTEGRATION_1C_GUIDE.md`) и загружает его в админке. Автоматическая синхронизация возможна только после установки отдельной программы на кассовый компьютер — это отдельный проект, требующий физического присутствия технического специалиста в магазине, не часть этой фазы.
- **Ручные правки не теряются при повторном импорте.** Если администратор вручную поправил, например, описание или фото товара на сайте, а потом загрузил новый файл из 1С с обновлённой ценой — описание и фото не должны затираться автоматически. Импорт обновляет только те поля, которые приходят из 1С (цена, остаток, наименование из 1С), и помечает защищённые вручную поля отдельным флагом, который impacting-импорт не трогает без явного подтверждения администратора.
- **Журнал изменений.** Каждый импорт пишет лог: сколько товаров добавлено, сколько обновлено, сколько исчезло (остаток 0 или не найдены в новом файле), какие ошибки.
- **Безопасность при сбое импорта.** Если файл не загрузился, пустой, повреждён или часть строк не распозналась — сайт **никогда** не должен обнулить остатки по всем товарам. Поведение при сбое: сохраняются последние успешно загруженные данные, администратору показывается баннер «последняя загрузка от [дата], возможно устарела», опционально — ограничение оформления заказа для товаров, чьи данные устарели дольше заданного срока (например, более 14 дней).
- **Админ проверяет импорт перед применением.** Перед тем как новые данные становятся видимыми покупателям, администратор видит сводку изменений (новые товары, изменённые цены, товары, которые пропадут) и подтверждает импорт.

### Задачи
1. Спроектировать модель данных: таблица товаров с `onec_id` как ключом, историей цен/остатков, флагами ручных правок.
2. Построить импорт CSV/XLSX с валидацией формата, построчным отчётом об ошибках.
3. Экран предпросмотра импорта (diff: новое / изменено / исчезнет) с кнопкой подтверждения.
4. Журнал импортов (дата, кто загрузил, результат) в админке.
5. Логика «не обнулять остатки при сбое» + баннер устаревших данных.

### Критерии готовности
- Загрузка тестового файла с несколькими строками (новый товар, изменённая цена, товар с нулевым остатком, повреждённая строка) даёт ожидаемый результат по каждому случаю.
- Повторная загрузка файла без изменений не трогает вручную отредактированные описания/фото.
- Имитация сбоя (пустой/битый файл) не обнуляет витрину и показывает предупреждение.

### Зависимости
Фаза 1 (нужна модель товара в каталоге).

## Фаза 3 — AI-помощник по карточкам товаров

**Текущий статус:** не начато.

### Принцип: полуавтоматический инструмент, не автономный скрапер
Администратор инициирует процесс для конкретного товара: указывает или подтверждает источник (страница производителя, официального дистрибьютора, либо другой источник, который не запрещает автоматическое обращение). Система предлагает черновик описания и варианты фото. **Публикация происходит только после подтверждения администратором.** Ничего не публикуется на сайт автоматически без просмотра человеком.

### Явные ограничения
- Не обращаться к vseinstrumenti.ru и аналогичным сайтам с защитой от ботов (капча при автозапросах) — это прямой запрет, не «технический вызов для решения».
- Не копировать чужие фотографии и тексты описаний буквально без прав на них — это нарушение авторского права конкурента. Инструмент должен формировать уникальный текст на основе фактов (характеристики, модель, производитель), а не копировать чужой текст.
- Источники — только те, что сам администратор указал или подтвердил для конкретной карточки; не произвольный обход интернета.

### Задачи
1. Инструмент в админке «Создать описание»: ввод/подтверждение ссылки на источник → черновик текста и предложенные фото → редактирование → публикация.
2. Хранение источника и даты формирования черновика (для разбора, если возникнет вопрос по содержимому карточки).
3. Явный запрет в коде на обращение к доменам с известной защитой от ботов (чёрный список доменов, начиная с vseinstrumenti.ru).

### Критерии готовности
- Ни одна карточка не публикуется без явного подтверждения администратора.
- Попытка указать как источник домен из чёрного списка — отклоняется с понятным сообщением.

### Зависимости
Фаза 2 (нужна модель товара с полем «описание» и флагом ручной защиты).

## Фаза 8 — Масштабируемость

**Текущий статус:** не начато, учитывается как требование к модели данных на будущее, не как отдельная немедленная задача.

### Задачи (задел на будущее, не блокирует текущий запуск)
1. Модель данных не должна жёстко привязывать товар к одному складу/магазину — закладывать поле `warehouse_id`/`store_id` с единственным значением сейчас, но без ограничения на одно значение в схеме.
2. Возможность нескольких источников импорта (разные 1С-базы или разные поставщики) — `onec_id` должен быть уникален в рамках источника, а не глобально, если появится второй магазин/поставщик.
3. Не закладывать в код предположение «один магазин = один населённый пункт» в текстах интерфейса (хранить адрес/название магазина как данные, не как хардкод в вёрстке).

### Критерии готовности
- Добавление второго склада/источника данных не требует миграции существующих `onec_id`.

### Зависимости
Фаза 2 (модель товара).
